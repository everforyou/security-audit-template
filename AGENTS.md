# Codex instructions — independent security audit

Read `README.md` and `SCOPE.md` at the beginning of each task. This workspace represents **one** authorized audit target. Do not assume that the target is a smart contract, web app, or any particular technology. Adapt tools and hypotheses to the actual code, deployment model, and engagement rules.

## Authorization and safety
- Work within `SCOPE.md`. Its local-only baseline allows broad reproduction against authorized target contents in an isolated researcher-controlled environment, including local state changes, synthetic roles, fuzzing, and exploit chains. Maximize coverage there without adding self-imposed restrictions. Remote targets, public/shared testnets, RPC providers, third-party services, and external callbacks require the exact scope entries and permission basis described in `SCOPE.md`; never infer permission from silence or from permission for a different asset, environment, identity, or method. Production writes, transactions, and persistent state changes are prohibited.
- Maximize production read-only validation when the written scope names the exact assets, query methods, identities, data boundaries, and rate limits. Do not infer this permission from a general audit authorization. Never perform production writes, broadcast transactions, or other persistent state changes; validate those paths only in explicitly authorized local, test, or staging environments. Third-party services still require explicit written permission. Do not retrieve or retain real user data or send it outside an approved environment; use public protocol state or synthetic records within the documented limits.
- Treat `target/` as an upstream checkout. Keep experiments in `poc/` or `scripts/`; do not silently modify the audited baseline. If a test needs a patch, document the patch and separately reproduce on unmodified target code.
- Keep hypothesis-specific PoC code under `poc/H-###/`, shared target-specific helpers under `poc/shared/`, and sanitized run records under `evidence/H-###/runs/<UTC-run-id>/`. Use `scripts/new-evidence-run.sh H-###` to prepare a unique run folder and manifest for every material attempt; it only creates local files and never executes a PoC. Complete the manifest after the attempt, then preserve the finalized run record unchanged. Never overwrite a prior run, and link its manifest from the hypothesis and any finding. Keep run output separate from PoC source.
- Keep cross-engagement hunting notes outside this one-target workspace. Reuse only target-independent, sanitized methods or fixtures after checking disclosure terms; never carry target code, reports, credentials, raw evidence, or authorization assumptions into another audit.
- Never commit secrets, access tokens, sensitive user data, or raw exploit material that could expose a live target. Sanitize evidence. Do not publish, submit reports, contact vendors, or create external issues without the user's explicit instruction.

## Working method
1. Read `SCOPE.md` and confirm the exact target revision or deployed version, permitted assets, exclusions, disclosure rules, and test limitations. Build a per-activity permission matrix from it. If remote scope is incomplete, state the gaps and hold only the activities those gaps affect; continue with the explicitly allowed local-only baseline and other clearly authorized work.
2. Inspect the actual codebase. Determine its language, framework, architecture, entry points, identities/roles, sensitive assets, external dependencies, and security invariants. Write the results to `research/architecture.md`.
3. Build a small, prioritized queue of **testable, code-grounded** hypotheses in `research/hypotheses.md`. For blockchain targets, first review recent fund-loss incidents in comparable protocols as described in `research/known-issues.md`, then map relevant mechanisms to this target's architecture and source. Prefer incidents whose exploit occurred within the three years before the audit; include older incidents when the mechanism remains present or the incident is seminal. Record source-reported severity separately from confirmed loss evidence, and use incidents to generate candidates—not as proof of a target vulnerability. Do not pad the queue with generic or speculative ideas to reach a count. Each hypothesis must name a concrete path or component, an attacker capability and precondition, the security property at risk, a plausible failure mechanism, and a validation method. If the evidence supports fewer candidates, report fewer and explain what further inspection would be needed.
4. Investigate hypotheses to the closure bar below using the broadest relevant test conditions the written scope permits. Cover applicable attacker roles, entry points, boundaries, input variants, and configurations; use authorized test accounts and staging environments when they are available and relevant. Respect stated rate, data, state-change, and stop limits. If a deployment-specific check is prohibited or unavailable, use the strongest safe local reproduction and leave that check pending instead of treating it as disproven. Keep each hypothesis ID stable, record every material attempt and its evidence, and carry unresolved candidates forward. Do not silently drop a candidate or replace it with a new weak candidate after one unsuccessful test. Keep test code in `poc/`; record precise setup, commands, outputs, traces, and before/after state in `evidence/` (without secrets).
5. Promote only demonstrated security issues to `findings/`, using `findings/FINDING_TEMPLATE.md`. Create one dossier folder at `findings/<finding-slug>/`, assign the next permanent ID in `findings/README.md`, and place the copied record in the dossier. Keep suspected issues and quality-only observations separately in research.
6. Check scope exclusions and documented known issues. When web access or prior-report evidence is unavailable, label duplicate and eligibility checks *pending*, not complete.
7. End each work session with a concise entry in `research/SESSION_LOG.md`: work performed, tests/results, confirmed findings, open questions, and the next concrete task.

### Hypothesis investigation and closure bar
- Give each candidate a permanent `H-###` ID. Do not delete, overwrite, or recycle IDs. If investigation reveals that a candidate is too broad, sharpen it or split it into linked child hypotheses while preserving the original record and explaining the change.
- Before testing, make the claim falsifiable: identify the relevant entry point or operation, attacker-controlled input/action, required permissions and environmental conditions, expected security invariant, and the specific consequence if the invariant fails. Cite the target version and relevant files, symbols, or lines.
- Trace the plausible path through the implementation: reachability, validation and authorization checks, the sensitive operation or sink, and relevant callers, consumers, or configuration. Record evidence that supports the candidate and evidence that could refute it.
- Design a validation exercise for the stated mechanism. Where the target and scope permit, run it deterministically against the unmodified baseline. Include a control or negative case when it helps show that the harness reaches the relevant path or that a guard distinguishes permitted from forbidden behavior. Exercise the meaningful roles, boundaries, and variants implied by the hypothesis; do not count an unrelated test or one failed payload as adequate coverage.
- Choose the strongest useful environment authorized for that test. When local reproduction cannot establish a deployment, identity, or configuration condition and a matching staging or other test environment is authorized, test that condition there within its recorded limits. Do not stop at a local pass/fail if the hypothesis depends on a distinct authorized environment; if that environment is not authorized or available, record the limitation and the exact validation still pending.
- For every attempt, create a new run folder and complete its `manifest.yaml` with the setup, exact command or action, tested version, permission basis, PoC revision/hash, expected result, actual result, sanitized output/trace paths, and what that result establishes. Link the run ID and manifest from the hypothesis record; do not copy full outputs into the hypothesis, session log, or finding. If a patched target is needed to explore a mechanism, document the patch and reproduce the security behavior on unmodified code before confirming a finding.
- Do not mark a hypothesis `disproven` just because a PoC failed, a test passed, a search found no example, or time ran short. Disproof requires documented evidence that the relevant attack path is unreachable or that the applicable guard/property holds across the material paths and preconditions in the hypothesis. A missing or invalid test setup is not counterevidence.
- Keep a candidate visible until it has a supported disposition. Use `blocked` when a concrete missing authorization, artifact, dependency, or environment prevents meaningful validation; say exactly what is needed. `Deferred` is not a shortcut after a failed attempt: first complete the source trace and a mechanism-specific validation attempt, then follow up on direct leads from its result. An exception requires documented evidence that testing is unavailable or materially lower priority; record the reason and a revisit trigger. Use `out of scope` only when mapping it to an explicit exclusion in `SCOPE.md`. These states are not evidence that the candidate is safe.
- Before moving past an unresolved candidate, either continue with the next concrete experiment or mark it `blocked`/`deferred` with the evidence already gathered and the exact next action or revisit trigger. Do not reset the queue by generating replacement hypotheses. At the start of a later session, resume the highest-priority unresolved candidate unless a documented scope change or new evidence changes the priority.
- Distinguish observation, hypothesis, and conclusion. A reproduced behavior is not a confirmed vulnerability until its realistic attacker path and security-boundary impact are demonstrated. A candidate may be closed as `disproven` only with the evidence bar above; otherwise preserve it as unresolved.

## Finding identity and program tracking
- Use `findings/README.md` as the authoritative ID, title, finding-status, submission-status, and program-response register.
- The default ID format is `F-001`, `F-002`, and so on. For a multi-component audit, document a stable project/component format in `README.md` before assigning IDs. Never renumber or reuse an ID.
- Keep technical finding status separate from whether a report was submitted. Mark a report submitted only when the dossier has evidence of sending; a filename or draft alone is insufficient.
- Record program responses such as accepted, duplicate, invalid/ineligible, rejected, needs information, or awaiting acknowledgment only from program correspondence. A local duplicate or prior-art assessment is not program feedback.
- Preserve submission and response dates, references, and evidence paths in the finding dossier. Mark missing or conflicting evidence unverified; do not infer submission or program feedback.

## Evidence and reporting
- For a submission-ready report, use `reports/SUBMISSION_TEMPLATE.md`. Include the explicit `## Proof of Concept` section with environment, steps, runnable code/command, expected versus actual result, and sanitized evidence. Do not submit without the user's explicit instruction.
- For email-based reporting, keep one canonical Markdown draft containing recipient and subject metadata plus the complete message body: greeting, short introduction, full report, and sign-off. Use the metadata for the email headers and copy from the greeting through the sign-off into the body. Do not maintain a separate cover-email draft unless the program or user asks for one.
- Do not attach the report Markdown or include it in an attachment archive. Keep any submission ZIP to the runnable PoC, reproduction instructions, and sanitized evidence; leave internal status notes outside the archive. Follow a program's portal or upload instructions when it explicitly requires a report file.
- Distinguish observation from interpretation and hypothesis. Cite paths, symbols, line numbers, and exact commit/build version.
- Describe realistic threat actors, permissions, required environmental conditions, exploit sequence, and specific technical impact. Do not manufacture a Critical/High rating; use the engagement's rubric when provided.
- A failing test is not automatically a security vulnerability. Establish that it violates a meaningful security boundary or property.
- If an exploit depends on extraordinary privileges or an unrealistic assumption, state that limitation explicitly.

## First task when asked to start
Review scope completeness, inspect target availability and version, discover reproducible build/test commands, summarize architecture and attack surfaces, and propose up to three highest-priority evidence-based hypotheses. For blockchain targets, incorporate recent, relevant fund-loss incident patterns after comparing them with the target's architecture and code. Aim for three only when inspection supports three concrete, testable candidates; do not invent details or pad the queue.
