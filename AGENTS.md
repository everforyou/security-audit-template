# Codex instructions — independent security audit

Read `README.md` and `SCOPE.md` at the beginning of each task. This workspace represents **one** authorized audit target. Do not assume that the target is a smart contract, web app, or any particular technology. Adapt tools and hypotheses to the actual code, deployment model, and engagement rules.

## Authorization and safety
- Use the broadest testing scope actually authorized by the bounty program or engagement; do not add self-imposed limits to an expressly in-scope asset, method, role, or environment. `SCOPE.md` authorizes isolated local reproduction and non-production testing of the in-scope target by default, including RPC-backed forks, target testnets, target test/staging deployments, local or remote state-changing reproduction, synthetic roles, fuzzing, and exploit chains; do not ask for redundant per-test permission. Check program rules for explicit exclusions, limits, and stop conditions and apply them at their full stated breadth. If one activity is explicitly excluded or ambiguous, hold only that activity and continue other available work. Never infer that a different asset or third-party target is in scope from credentials or target authorization. Production writes, transactions, and persistent state changes are prohibited.
- Maximize production read-only validation only when written scope names the exact assets, query methods, identities, data boundaries, and rate limits. Do not infer production-read permission from general audit authorization. Never perform production writes, broadcast transactions, or other persistent state changes; validate those paths in local, fork, testnet, or staging environments. Public target data may be accessed through target or provider endpoints under their published terms and limits; testing a third-party service or asset itself requires its own authorization. Do not retrieve or retain real user data or send it outside an approved environment; use public protocol state or synthetic records within documented limits.
- Treat `target/` as an upstream checkout. Keep experiments in `poc/` or `scripts/`; do not silently modify the audited baseline. If a test needs a patch, document the patch and separately reproduce on unmodified target code.
- Keep hypothesis-specific PoC code under `poc/H-###/`, shared target-specific helpers under `poc/shared/`, and sanitized run records under `evidence/H-###/runs/<UTC-run-id>/`. Use `scripts/new-evidence-run.sh H-###` to prepare a unique run folder and manifest for every material attempt; it only creates local files and never executes a PoC. Complete the manifest after the attempt, then preserve the finalized run record unchanged. Never overwrite a prior run, and link its manifest from the hypothesis and any finding. Keep run output separate from PoC source.
- Keep cross-engagement hunting notes outside this one-target workspace. Reuse only target-independent, sanitized methods or fixtures after checking disclosure terms; never carry target code, reports, credentials, raw evidence, or authorization assumptions into another audit.
- Never commit secrets, access tokens, sensitive user data, or raw exploit material that could expose a live target. Sanitize evidence. Do not publish, submit reports, contact vendors, or create external issues without the user's explicit instruction.

## Working method
1. Read `SCOPE.md` and verify current program rules from authoritative sources (browse official program pages when available), exact target revision/deployment, eligible impact, explicit exclusions and limits, proof requirements, and stop conditions. Record the source and date. The default permits non-production testing of the in-scope target; if one activity is explicitly excluded or unclear, hold only that activity and continue the rest.
2. Inspect the actual codebase. Determine its language, framework, architecture, entry points, identities/roles, sensitive assets, state transitions, configurations, external dependencies, security invariants, and available local/test/staging environments. Write the architecture and attack-surface/condition inventory to `research/architecture.md`.
3. Build a coverage-led queue of all **testable, code-grounded** hypotheses supported by the architecture; there is no fixed candidate-count limit. Rank candidates by plausible impact, reachability, novelty, and bounty eligibility. For blockchain targets, first review recent comparable fund-loss incidents as described in `research/known-issues.md`, then map relevant mechanisms to this target's architecture and source. Prefer incidents whose exploit occurred within the three years before the audit; include older incidents when the mechanism remains present or the incident is seminal. Keep source-reported severity separate from confirmed loss evidence. Do not pad with generic ideas, but do not stop at a short shortlist while material attack surfaces remain unreviewed. Each hypothesis must identify a concrete path, attacker capability and precondition, security property at risk, plausible failure mechanism, novelty/eligibility screen, and validation plan.
4. Investigate each hypothesis to the closure bar below. Derive test cases from the actual code paths, roles, trust boundaries, state/configuration variants, and deployment assumptions. Use local reproduction by default and every relevant authorized environment that can resolve a distinct condition; do not stop at one happy-path test, a harness error, or a local result when the claim depends on deployed behavior. Track each material case as tested, failed, inconclusive, blocked, or not applicable with its run evidence and rationale. If a remote test is unauthorized or unavailable, leave that environment-specific result open while completing independent local checks. Keep hypothesis IDs and prior attempts stable; never silently drop a candidate. Keep PoCs in `poc/` and sanitized evidence in `evidence/`.
5. Promote only demonstrated security issues to `findings/`, using `findings/FINDING_TEMPLATE.md`. Before calling a finding submission-ready, complete the program eligibility and public/local duplicate review, verify the required proof and report format, and keep any uncertain check pending. Create one dossier folder at `findings/<finding-slug>/`, assign the next permanent ID in `findings/README.md`, and link its hypotheses, PoCs, run manifests, and eligibility/novelty evidence.
6. Check the complete local finding history and public prior art, including program-known issues and current exclusions. When web access or records are unavailable, label duplicate and eligibility checks *pending*, not complete. Recheck current rules and prior art before submission.
7. End each work session with a concise entry in `research/SESSION_LOG.md`: work performed, tests/results, confirmed findings, open questions, and the next concrete task.

### Hypothesis investigation and closure bar
- Give each candidate a permanent `H-###` ID. Do not delete, overwrite, or recycle IDs. If investigation reveals that a candidate is too broad, sharpen it or split it into linked child hypotheses while preserving the original record and explaining the change.
- Before testing, make the claim falsifiable: identify the relevant entry point or operation, attacker-controlled input/action, required permissions and environmental conditions, expected security invariant, and the specific consequence if the invariant fails. Cite the target version and relevant files, symbols, or lines.
- Before the first attempt, create a hypothesis-specific coverage plan. List material attacker roles, entry points, boundaries, preconditions, state/configuration variants, and environments that could change the outcome. For each, state why it matters, the expected secure/unsafe result, a control or negative case where useful, and where it can be tested. Mark dimensions not relevant with a code-based reason; do not silently omit them. This plan tracks test coverage, not permission.
- Trace the plausible path through the implementation: reachability, validation and authorization checks, the sensitive operation or sink, and relevant callers, consumers, or configuration. Record evidence that supports the candidate and evidence that could refute it.
- Validate that the harness reaches the intended operation before interpreting an attack result. Use a control, trace, assertion, or equivalent evidence of path reachability; an exception, timeout, missing fixture, or failing setup is inconclusive and requires repair or a different experiment.
- Exercise every material case in the coverage plan against the unmodified baseline, including boundaries and role changes that could affect the mechanism. Use clean or reinitialized state for independent cases; repeat when behavior is nondeterministic or stateful. There is no arbitrary payload count: coverage is adequate when each code-grounded condition that could change the conclusion has evidence or a documented reason it cannot apply.
- Choose the strongest useful environment actually authorized. If a claim depends on deployed configuration, identity, state, chain height, or service behavior, use an authorized matching test/staging/testnet environment when available. Do not treat a local result as resolving a distinct deployment condition. If that environment is unavailable or unauthorized, keep that case pending and continue all local and other authorized cases.
- For every attempt, create a new run folder and complete its `manifest.yaml` with the setup, exact command or action, tested version, permission basis, PoC revision/hash, expected result, actual result, sanitized output/trace paths, and what that result establishes. Link the run ID and manifest from the hypothesis record; do not copy full outputs into the hypothesis, session log, or finding. If a patched target is needed to explore a mechanism, document the patch and reproduce the security behavior on unmodified code before confirming a finding.
- Do not mark a hypothesis `disproven` just because one PoC failed, a test passed, a search found no example, or time ran short. Disproof requires documented evidence that the relevant attack path is unreachable or the invariant holds across every material case in the coverage plan. A missing or invalid test setup is not counterevidence; any untested material case must stay open, blocked, or not applicable with a reason.
- Keep a candidate visible until it has a supported disposition. A blocked environment blocks that case, not the whole hypothesis, when local or other authorized validation remains possible. Use overall `blocked` only when no meaningful authorized work can proceed; state exactly what is needed and the next action. `deferred` is not a shortcut after one failed attempt: first complete the source trace, coverage plan, mechanism-specific local attempt, and direct follow-ups, then document why remaining work is materially lower priority and give a revisit trigger. If a specific test cannot run because an artifact, dependency, or environment is missing, mark that case `blocked`; do not defer the whole hypothesis while other meaningful work remains. Use `out of scope` only when mapping to a specific written exclusion in `SCOPE.md`. These states are not evidence that the candidate is safe.
- Before moving past an unresolved candidate, either continue with the next concrete experiment or mark it `blocked`/`deferred` with the evidence already gathered and the exact next action or revisit trigger. Do not reset the queue by generating replacement hypotheses. At the start of a later session, resume the highest-priority unresolved candidate unless a documented scope change or new evidence changes the priority.
- Distinguish observation, hypothesis, and conclusion. A reproduced behavior is not a confirmed vulnerability until its realistic attacker path and security-boundary impact are demonstrated. A candidate may be closed as `disproven` only with the evidence bar above; otherwise preserve it as unresolved.

## Finding identity and program tracking
- Use `findings/README.md` as the authoritative ID, title, finding-status, submission-status, and program-response register.
- Keep the researcher's eligibility/novelty screen separate from technical validation and official program feedback. A technically confirmed issue can still be known, out of scope, or ineligible; do not present a pending or local screen as a program decision.
- The default ID format is `F-001`, `F-002`, and so on. For a multi-component audit, document a stable project/component format in `README.md` before assigning IDs. Never renumber or reuse an ID.
- Keep technical finding status separate from whether a report was submitted. Mark a report submitted only when the dossier has evidence of sending; a filename or draft alone is insufficient.
- Record program responses such as accepted, duplicate, invalid/ineligible, rejected, needs information, or awaiting acknowledgment only from program correspondence. A local duplicate or prior-art assessment is not program feedback.
- Preserve submission and response dates, references, and evidence paths in the finding dossier. Mark missing or conflicting evidence unverified; do not infer submission or program feedback.

## Evidence and reporting
- For a submission-ready report, use `reports/SUBMISSION_TEMPLATE.md` and adapt it to current program instructions. Include the explicit `## Proof of Concept` section with environment, steps, runnable code/command, expected versus actual result, and sanitized evidence. Complete eligibility and novelty checks first. Do not submit without the user's explicit instruction.
- For email-based reporting, keep one canonical Markdown draft containing recipient and subject metadata plus the complete message body: greeting, short introduction, full report, and sign-off. Use the metadata for the email headers and copy from the greeting through the sign-off into the body. Do not maintain a separate cover-email draft unless the program or user asks for one.
- Do not attach the report Markdown or include it in an attachment archive. Keep any submission ZIP to the runnable PoC, reproduction instructions, and sanitized evidence; leave internal status notes outside the archive. Follow a program's portal or upload instructions when it explicitly requires a report file.
- Distinguish observation from interpretation and hypothesis. Cite paths, symbols, line numbers, and exact commit/build version.
- Describe realistic threat actors, permissions, required environmental conditions, exploit sequence, and specific technical impact. Do not manufacture a Critical/High rating; use the engagement's rubric when provided.
- A failing test is not automatically a security vulnerability. Establish that it violates a meaningful security boundary or property.
- If an exploit depends on extraordinary privileges or an unrealistic assumption, state that limitation explicitly.

## First task when asked to start
Review current program rules and scope completeness, inspect target availability/version, discover reproducible build/test commands, and produce an architecture plus attack-surface/condition inventory. Start a prioritized queue for every concrete candidate supported by inspection; do not cap it at three or pad it with speculation. Retain the full queue and open coverage gaps while identifying the next highest-priority candidates. For blockchain targets, incorporate recent relevant fund-loss patterns after mapping them to the target's actual architecture and code.
